# Reading a whole document

Hand `<SpokenText>` elements instead of a string and it reads the lot:

```tsx
<SpokenText>
  <h2>What is living in there</h2>
  <p>Wild yeasts eat the sugars in the flour…</p>
  <h2>Feeding it</h2>
  <p>One part starter, five parts flour, five parts water…</p>
</SpokenText>
```

The structure is kept. An `h2` stays an `h2`, a link stays a link, a class
stays where it was written; only the text leaves are replaced, by a span per
word. Nothing about the page changes except that it can now be read to you.

[An article, read end to end](/article) is the whole pattern running.

## One block at a time

Each heading, paragraph, list item and blockquote is its **own** alignment
request. That is what makes a long page possible rather than merely slow:

- Each block caches on its own, so editing one paragraph does not reprice the
  page.
- The first block is fetched on mount, and the next is warmed while the current
  one plays.
- Clicking a word in a block nobody has asked for yet fetches that block and
  starts there.

`currentWordIndex` is one number across the whole document, and `segments` says
where each block begins and ends, so a table of contents or a progress bar can
be built from it. Until every block has landed, `duration` counts the rest at a
reading pace and `durationIsEstimate` says so, which is why `<Player>` shows
the total dimmed and marked with a tilde: `~1:42`.

A string is a document with one block, so nothing about a single passage
changes.

## A player anywhere on the page

`<SpokenTextProvider>` holds the controller, so the play button does not have
to be a sibling of the text:

```tsx
import { Player, SpokenText, SpokenTextProvider } from "spoken-text";

<SpokenTextProvider>
  <header className="sticky top-0">
    <Player />
  </header>

  <article>
    <SpokenText>{/* the whole document */}</SpokenText>
  </article>
</SpokenTextProvider>;
```

One document per provider. It takes the same options as the hook and applies
them to the whole document, and anything written on the `<SpokenText>` inside
it wins, so a `debounceMs` can sit next to the text it is about.
`useSpokenTextController()` returns the controller it is holding, for building
a player of your own.

## Leaving things unspoken

Code read aloud as prose is noise, and it would wreck the alignment besides. So
`code`, `pre`, `kbd`, `samp`, `var`, `script`, `style`, `svg`, `canvas`,
`iframe` and `math` are skipped by default.

Skipped content still renders, untouched, exactly where it is. It is dropped
only from the text handed to the aligner, so an inline `<code>` in the middle
of a sentence leaves a gap in what is said and the words on either side stay
correctly timed.

```tsx
<SpokenText skip={["code", "pre", "figcaption", ".footnote"]}>…</SpokenText>
<SpokenText skip={(el) => el.type === "aside"}>…</SpokenText>
<SpokenText only={[".prose"]}>…</SpokenText>
```

Both props take an array of selectors: a tag (`"pre"`), a class
(`".footnote"`), an attribute (`"[aria-hidden]"`), or a predicate over the
React element. `only` fences the field; `skip` cuts inside it.

Per element, `data-spoken` and `data-spoken-skip` do the same job at the point
of authorship, which is what you want in MDX. The reference tables in these
docs are marked that way: a list of type signatures read aloud is noise.

Headings are read. `skip={["h1", "h2", "h3"]}` is the opt-out.

## The component boundary

React children are opaque until they are rendered, so the walk sees the
elements you hand it and nothing inside a component of your own.

```tsx
// Reads nothing: MyArticle is a closed box.
<SpokenText>
  <MyArticle />
</SpokenText>
```

MDX output is fine, because MDX hands you real `h2` and `p` elements. So are
hand-written pages. This one is MDX, and the player at the top of the column is
reading it.

## What each block is

Every block says what it is, so a voice can read a title like a title. The
client sends `{ content, kind }`, where `kind` is `"heading"`, `"paragraph"`,
`"list"` or `"quote"`, and the handler passes it on to the speech adapter.

Headings are `h1`–`h6`, list items are `li`, quotes are `blockquote`, and
everything else is a paragraph. A block that does not say what it is, a `p` or
a `div`, keeps the kind it sits inside, so the paragraph markdown puts inside a
blockquote is still read as a quote.

`kind` is part of the cache key, so the same words as a heading and as a
paragraph are two recordings. It is reported back on the client as
`segments[].kind`, and it reaches the request body of your own
`fetchAlignment` too.

## Saying what is not on the page

Some of what a reader takes in is not text. A section number is implied by the
layout; an image says what it says without words; a code sample is
deliberately silent. `say` fills those gaps, and only in the audio.

```tsx
<SpokenText
  say={{
    h2: ({ text, count }) => `Section ${count}: ${text}`,
    img: ({ element }) => element.props.alt,
    pre: () => "Code sample skipped.",
  }}
>
  …
</SpokenText>
```

It is a map of selector to rule. The selectors are the ones `skip` and `only`
take: a tag, a `.class`, an `[attr]`. The first matching key wins.

```ts
say?: Record<string, (info: {
  text: string;
  element: ReactElement;
  count: number;
  kind: BlockKind;
}) => string | { before?: string; after?: string } | null | undefined>;
```

Each rule is called with the element it matched:

<Props data-spoken-skip>
  <Prop name="text" type="string">
    The element's own spoken text, and `""` for an element that is skipped.
  </Prop>
  <Prop name="element" type="ReactElement">
    The element itself, which is where an `alt` or a `title` lives.
  </Prop>
  <Prop name="count" type="number">
    Which match this is, 1-based, per rule, in document order. A rule on `h2`
    counts only the `h2`s.
  </Prop>
  <Prop name="kind" type="BlockKind">
    What the block is: `"heading"`, `"paragraph"`, `"list"` or `"quote"`.
  </Prop>
</Props>

Return a string and it replaces the element's spoken text. Return
`{ before, after }` and it wraps what is already there. Return `null` or
`undefined` and the rule stands aside, so a rule can decide case by case.

A rule on a **skipped** element speaks in its place, which is the point of the
`pre` example above: the code stays out of the audio and the reader is told
that something was left out rather than hearing a paragraph end and another
begin with nothing between them.

Injected words are spoken but never rendered. They are hidden tokens in the
word list, marked `hidden` on the `DisplayWord`, so the words on the page keep
their exact timings and the highlight does not drift while something unwritten
is being said.
